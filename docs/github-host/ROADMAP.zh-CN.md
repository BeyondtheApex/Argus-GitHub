# GitHub 宿主：优化路线与创新点

> 状态：提案，欢迎讨论。由 [kalijerry/Argus-GitHub](https://github.com/kalijerry/Argus-GitHub) 维护者整理，基于 `github-host` 分支 2026-11-19 的代码。

## 结论

宿主层（`argus/github_host/`）已经把“状态放 Git、Actions 执行”做得很扎实，再往这里堆功能收益不大。下一步的重心应该从“能跑”转到“能证明”：用故障注入证明中断可恢复，用评测集证明多角色值回成本，再在这两样证据之上做差异化。

建议把创新押在三件事上，按优先级：

1. **副作用只发生一次的可靠性语义**，并配一套自动化的“断点混沌测试”来证明它。
2. **工作流结晶**：重复出现的任务由 Agent 提炼成确定性流程，模型只处理例外，并用 `surprise` 事件决定何时退回模型。
3. **按可逆性分级的能力清单**：审批只花在真正不可逆的动作上，并且审批本身可度量。

“按能力路由到异构自托管机器”保留为第四个方向，等 Rust 单仓库跑通后再做。

## 现状对照

底层机制大多已经有了，缺的是“证明”和“声明式策略”两类东西。

| 目标 | 现状 | 依据 | 缺口 |
| --- | --- | --- | --- |
| 中断后下一轮能接着完成 | Git CAS、先写 outbox 再派发、找回丢失的 run、控制器产物恢复 | `host.py` `flush_dispatches` / `reconcile_runs`，`recovery.py` | 没有针对各中断点的系统性故障注入验收 |
| 交接保存“不要再试的方向” | 原生记忆与失败记录完整保留，验证失败回灌给主控 | `delivery.py` `reconcile_deliveries` | 没有结构化的“死路”字段 |
| 摘要带水位 | 宿主不做摘要，投影在状态变化时丢弃 | `projections.py` | 角色摘要的水位仍在原生层，未显式记录 |
| 确定性命名 + 先查再建 | 先按分支查 PR 再创建，PR 带 workspace 标记 | `delivery.py` `_delivery_for_revision` | 分支名不含尝试次数 |
| 批准绑定内容哈希 | 已实现 | Issue intake | 无 |
| 授权分级 | 跑模型的 job 无写权限；受保护路径强制人工合并 | `delivery.py` `requires_manual_review` | 受保护路径是硬编码列表，没有显式等级 |
| 不可逆操作默认拦下 | 禁止发布凭据、workflow、符号链接；`auto_merge` 默认关 | `delivery.py` `publish_candidate` | 没有能力清单和补偿动作；外部工具调用不保证只执行一次 |
| 多角色是否值得 | 完整保留四角色；升级门禁要求真实模型对比证据 | `evaluation.py` | 门禁有了，评测集和跑分工具没有 |
| `surprise` 事件与审批指标 | 未实现 | — | 整块待做 |
| 模板仓库 + 独立平台仓库 | fork 模式，平台与项目同仓库 | 部署文档第 1 步 | 路由策略和控制代码在项目仓库里 |
| 第一阶段只做 Rust | 默认验证命令是 Python pytest | `.argus-host/config.json` | 没有 Rust profile，编译与写入未拆成两个 job |

## 已知风险点

1. **重试撞上已关闭的 PR（已修复）。** 候选被拒后重试会接管已关闭的 PR，head 检查失败，任务永远无法交付。现在只接管打开且带标记的 PR。
2. **验证派发没有走 outbox。** `flush_dispatches` 先发出验证 workflow 再把 `validation_pending` 改成 false，中间断电会重复跑一次验证。后果只是多一次 CI，但说明“先记意图”还不是统一机制。
3. **副作用边界散落各处。** 推分支、开 PR、合并、派发 run、取消 run 各自处理幂等，没有一张表列出“系统会对外做哪些事”，故障注入只能靠人工挑点。

## 创新点

### 1. 副作用账本 + 断点混沌测试（最优先）

把所有对外动作统一成一种记录：`意图 → 执行 → 观察 → 对账`，每条带确定性的外部身份（分支名、PR 标记、run 标题）。有了这张账本，系统就能**自动枚举每一个副作用边界，在每个边界前后各杀一次进程**，然后断言：任务最终完成、外部对象不重复、已完成的步骤不重做。

“push 之前”“PR 已创建、结果还没写回”“测试失败、失败记录已写入”这三个中断点是这套框架的特例。差异化在于“可证明”：很少有 Agent 系统能拿出“每个断点都杀过”的报告。

### 2. 工作流结晶

同类任务成功几次后，由 Agent 把做法提炼成确定性脚本或 workflow，附带测试；之后同类任务先走脚本，失败或输入超出预期时才调用模型。Pi 后端的[项目工具自进化](../pi-runtime-learning.md)已经是一个小版本，方向是从“单个函数”扩到“整段流程”。

反向通道：结晶流程遇到意外时发出 `surprise` 事件，意外率超过阈值就自动退回模型。衡量指标是同类任务的模型调用数和成本随时间下降。

### 3. 按可逆性分级的能力清单

把 `delivery.py` 里的硬编码保护路径换成声明式清单：每个能力写明写入目标、是否离开系统边界、补偿动作和补偿测试。没写的一律按不可逆处理并转给人。审批请求由清单自动生成（变化、异常、为什么不可逆），高风险项要求审批人输入内容，并记录审批耗时与通过率。

它与创新点 1 是同一张表的两面：账本记录“做了什么”，清单规定“能做什么、做错了怎么撤”。

### 4. 按能力路由到异构自托管机器（后置）

宿主已经支持按资源 profile 选 Runner。下一步是把路由策略移出项目仓库（Org 级 runner group），并支持硬件在环。它依赖前三项：不可信代码上真实硬件，必须先有可逆性分级和可证明的恢复。

## 路线图

| 阶段 | 内容 | 退出门槛 |
| --- | --- | --- |
| M0 内核加固 | 副作用账本 + 断点混沌测试 | 每个副作用边界前后都杀过一次进程；任务都能完成，无重复 PR，已完成步骤不重做 |
| M1 Rust 单仓库 | 单 Engineer 模式（配置开关，保留四角色代码），模板仓库建项目 | 模板新建的 Rust 仓库从 Issue 走到 PR，中断可续；编译与写入分属两个 job，`cargo publish`、tag 等动作被拦下 |
| M2 评测集 | 从 [Rust-SWE-bench](https://arxiv.org/abs/2602.22764) 取 tokio-rs/bytes、chrono、fd 共 24 题 | 单角色基线跑完，每题至少 3 次；记录每次成功修复的成本、人工介入次数、隐藏测试通过率 |
| M3 加 Reviewer | 同一评测集 A/B 对比；上线 `surprise` 事件与审批指标 | Reviewer 的净收益在评测上可见才保留 |
| M4 结晶与扩展 | 工作流结晶试点，第二门语言 | 同类任务的模型调用数随时间下降；意外率超阈值时自动退回模型 |

M0 不依赖模型凭据；M2 之后每一步都要花真实模型费用，预算沿用现有配置，由 API key 自身限额兜底。

### 评测集选择

| 仓库 | 类型 | Rust-SWE-bench 题数 | 理由 |
| --- | --- | --- | --- |
| tokio-rs/bytes | 底层库 | 22 | 体量小、依赖极少、测试快，适合先跑通流水线 |
| chronotope/chrono | 应用库 | 17 | 日期时间边界题多，隐藏测试区分度高 |
| sharkdp/fd | 命令行工具 | 12 | 端到端 CLI 行为，与前两个库类题互补 |

从 51 题中按难度分层挑 24 题（每仓 8 题）。备选 clap（56 题），过程宏依赖重，留到编译与写入拆分验证之后。

## 不建议作为卖点的

- 四角色分工本身：在评测集证明独立 Reviewer 值回成本前，它只是假设。
- 状态放 Git、Pages 工作台：是好的工程，但不是差异。
